# 開発レポート作成

## 利用場面と入力

開発状況、変更内容、要件対応、検証結果をレポートにする依頼で使用する。リポジトリルートの `AGENTS.md`、`docs/requirements.md`、`README.md` を先に読む。詳細仕様はこれらを正規資料とし、このスキルに複製しない。

入力は現在のコードとテスト、最新の依頼・要件、既存文書・レポート、確認可能なGit履歴と未コミット差分。履歴や会話が取得できない部分は推測せず欠落として示す。

## 手順

1. 作業ルート、適用指示、Git状態、既存の文書構成を確認する。`rg --files --hidden` などの探索では依存・生成・Git内部を除外し、利用者の保存データや認証情報を開かない。`git log --oneline`、対象差分で関連変更を特定する。
2. 最新要件を正規要件書と照合する。利用者要求・採用した解釈・コード実装・将来構想・未確認を区別する。矛盾や仕様との差は明示し、レポート依頼を根拠にアプリを修正しない。
3. 重要な処理を入口から結果まで読む。入力補助からフォーム・検証・保存、優先度と整列、読み戻し、待受など、依頼に関係する経路とテストの実際のアサーションを確認する。名前やラベルの存在だけで機能完成と判定しない。
4. `AGENTS.md` の変更別方針に従い必要な検証を選ぶ。既存テストやビルドを使い、コマンド・作業ディレクトリ・終了状態・実行件数・スキップ・失敗を記録する。起動検証を行うならlocalhost限定を守り、実ソケットと代表HTTP応答を調べ、自分が起動したプロセスのみ停止する。外部公開・トンネルは使わない。文書確認のみで十分なら、動作検証を未実施と明記する。
5. 下記の出力を簡潔にまとめる。過去の成功を今回の実行結果と混同せず、失敗や残課題を隠さない。モック・DOM検証と実ブラウザー・実機検証を区別する。
6. 保存前にリンク・パス・コマンド定義・架空例・現行仕様との整合を確認する。差分でアプリと利用者データが変わっていないことを確認する。GitHubへの反映は利用者の依頼範囲に従い、コミット・プッシュの成否も事実どおり報告する。

## 出力と保存先

- 対象・確認基点（HEADと関連する未コミット変更）、実現した操作。
- 要件対応表：要求、実装状況、コード・テストなどの根拠、差や未確認。
- 検証根拠：今回実行したコマンドと結果／コードを読んだ確認／過去記録／未実施を分ける。
- 制約、未確認事項、阻害要因、次の作業と必要資料。

依頼が保存を求めた場合は指定先、既存レポートの場所、既存文書の適切な節の順に選ぶ。現状は独立レポートの慣例がないため、単発の報告はチャットを基本とし、保存が必要なら `docs/` に目的の明確な文書を置く。要件書は状況一覧の正規参照先、READMEは利用手順として維持し、同じ詳細仕様を複数箇所に複製しない。

## 禁止事項

実行していない検証を成功と記載しない。利用者の登録データ、バックアップ、実在アカウントの表示名・ID・紐づく配置、秘密情報を転載しない。例は明示的な架空情報と説明用の予約ドメインを使う。レポート作成だけの依頼ではアプリ・テスト・依存・起動設定を変更せず、利用者データの修正や移行も行わない。将来機能や型だけの準備を実装済み機能として扱わない。
