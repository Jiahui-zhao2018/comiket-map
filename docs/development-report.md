## 1. 現在できること

1. PCのチェックアウトで `npm ci`、`npm run dev` を実行し、`http://127.0.0.1:5173/` を開く。停止は起動ターミナルでCtrl+C。バックエンドやアカウント登録は不要。
2. 「開催回を追加」で名前、日目、ホール候補を設定する。複数の開催回を切り替えて管理できる。候補の入力順が一覧の整列順となる。
3. サークル登録フォームで名前・日目・ホール・場所を入力し、5個の星から優先度1〜5を選ぶ。URLまたはXの@ユーザー名は任意。優先度の初期値は3、5が最高。すべて手入力でも使える。
4. 入力補助を使う場合、Xの表示名の文字列を貼り付けて「読み取る」。原文、名前・日目・エリア・場所の候補、不足や曖昧さの説明が表示される。Xへの問い合わせはない。
5. 「候補をフォームに反映」で認識済み項目を上書きする。確認チェックボックス・反映時の確認ダイアログはない。認識できない／確定できない項目は元の値を保持する。人物名とサークル名が同じとは限らないため、フォーム上で修正する。この時点では保存されない。
6. 「登録する」または「変更を保存」で検証後に保存する。必須不足や不正入力はブラウザー標準検証または画面内エラーで案内する。成功した登録・編集・削除はlocalStorageへ反映される。
7. 一覧は日目の設定順→ホールの設定順→優先度降順→名前→IDで整列。検索と日目・ホールの絞り込み、編集・削除ができる。削除には確認ダイアログがある（入力補助の確認不要とは別）。同一ブラウザープロファイル・同一オリジンで再度開くと保存内容を復元する。
8. 全開催回をJSONへ書き出せる。読み戻しは検証・置換確認後に全開催回を入れ替える。マージや端末同期ではない。読み戻しの置換確認も入力補助とは別の操作。

マップ・訪問ルートのタブは「準備中」。一覧の未配置表示は使えるが、地図上で確認・修正する操作はまだない。

## 5. 重要な設計判断と制約

- React＋TypeScript＋Viteの静的Webアプリ。READMEの採用理由は個人利用でバックエンド運用を避け、後続拡張に型を利用すること。クラウド同期の仕組みはない。
- データはversion 1のJSONとlocalStorage。ホスト名・ポート・プロファイルに依存し、データ消去やプライベートモードで失われ得る。読み戻しは全件置換で、同時編集の競合解決もない。定期的なJSONバックアップが必要。
- 場所の原文と確認済み座標を別にする。位置に影響する変更は座標確認を解除する。配置データの出所・確認工程が重要で、型があるだけでは公式位置を得られない。
- 表示名はローカルの正規表現解析。日目は数字＋日目、配置は英字・カタカナ1文字と1〜2桁の番号、任意のa/b系接尾辞が中心。漢数字・曜日だけの日目、ひらがな／複数文字ブロック、島・机などの独自表現、複雑な省略配置は非対応。ホール番号を表示名から直接特定する処理もない。名前は最初の日目／配置より前を切り出すため、特殊な名前・並びでは誤候補になり得る。
- 反映済みの値も必ず利用者が修正できる。複数候補の検出はヒューリスティックで、公式配置の存在検証・誤抽出の完全排除はしていない。
- 既知の文言不整合：validLinkはHTTP/HTTPSを受理するが、CircleFormのエラー文はHTTPSのみを案内する。今回修正していない。
- アクセシビリティはネイティブラジオ・ラベル・数値表示・フォーカス枠を実装。ただし実際の読み上げやモバイルの使いやすさを検証したわけではない。
- localhost限定は公開範囲の設定であり、登録した外部リンクを利用者が開く操作まで遮断するものではない。

4. **日目別の手動訪問ルートを追加**：既存routesを使う編集UI、同一ホール内の線・矢印、日目・ホール変更時の整合性を実装する。自動最適化は含めない。
5. **PDFからの候補位置取得を小規模検証**：上記資料の一部で文字と座標の対応を確認し、人の確認を経て取り込む。PDFテキスト抽出だけで位置認識成功と判定しない。失敗しても確認済み位置による地図・ルートを使えるようにする。
